# Architecture: Internal Note on Product Variant

## Verified Architecture

Independently re-confirmed every load-bearing claim from `technical-discovery.md` against the actual installed `@vendure/core` 3.7.2 / `@vendure/dashboard` 3.7.2 package and this project's own files (not taken on the Technical PM's word):

1. **`public?: boolean` on a custom field controls Shop API exclusion, structurally (not just access-checked).**
   `node_modules/@vendure/core/dist/api/config/graphql-custom-fields.js:43`:
   ```js
   return !config.internal && (publicOnly === true ? config.public !== false : true);
   ```
   The Shop API schema is built with `publicOnly = true`; the Admin API schema is built with `publicOnly = false`. A field with `public: false` is filtered out before the Shop API schema is even assembled.

2. **`ProductVariant` is a valid `customFields` key.**
   `node_modules/@vendure/core/dist/config/custom-field/custom-field-types.d.ts:196`: `ProductVariant?: CustomFieldConfig[];`

3. **The Dashboard already renders `ProductVariant` custom fields with no plugin/UI code.**
   `node_modules/@vendure/dashboard/src/app/routes/_authenticated/_product-variants/product-variants_.$id.tsx:302`:
   ```tsx
   <CustomFieldsPageBlock column="main" entityType="ProductVariant" control={form.control} />
   ```
   This is already present in the shipped variant detail page and resolves fields dynamically from server config.

4. **This project needs a real migration; there is no auto-sync path in use.**
   `src/vendure-config.ts:45-53` — `synchronize: false`, plus a comment directly above `customFields: {}` (line 57-58) reading: *"When adding or altering custom field definitions, the database will need to be updated. See the 'Migrations' section in README.md."* — the project's own scaffold already anticipates this exact situation.
   `README.md` "Migrations" section confirms the workflow: `npx vendure migrate` generates a file into `src/migrations/`, which is then run automatically by `runMigrations()` in `src/index.ts` on next server start.
   `package.json` confirms `@vendure/cli` (3.7.2) is present as a devDependency, so `npx vendure migrate` is available; there is no dedicated `migrate` npm script, so the CLI command must be run directly.
   `src/migrations/` does not exist yet — this will be the first migration generated for this project.

No claim from the upstream documents needed correction — all four held up under direct inspection.

## Design Principle Applied

The smallest possible extension that follows an existing, framework-provided pattern: a single `customFields.ProductVariant` entry. No new entity, no new plugin, no new resolver, no new UI component — introducing any of those would be inventing a parallel mechanism next to one Vendure already ships for exactly this purpose.

## Proposed Design

Add one custom field definition to `src/vendure-config.ts`:

```ts
customFields: {
    ProductVariant: [
        {
            name: 'internalNote',
            type: 'text',
            nullable: true,
            public: false,
            label: [{ languageCode: LanguageCode.en, value: 'Internal note' }],
            description: [{ languageCode: LanguageCode.en, value: 'Internal-only note for warehouse/product staff. Never shown to customers.' }],
        },
    ],
},
```

`type: 'text'` (multi-line) rather than `'string'` (single-line) is chosen per the Technical PM's stories, which call for holding multi-sentence notes comfortably.

`LanguageCode` needs to be imported from `@vendure/core` alongside the existing imports in `vendure-config.ts`.

## Files to Create/Modify

- **Modify**: `src/vendure-config.ts` — add the `internalNote` entry under `customFields.ProductVariant`, and add `LanguageCode` to the existing `@vendure/core` import.
- **Create**: one migration file under `src/migrations/` — generated by running `npx vendure migrate` after the config change, not hand-written. This also creates the `src/migrations/` directory itself, since it doesn't exist yet.

No other files need to change. No Dashboard code, no plugin, no resolver, no GraphQL schema file.

## Registration/Configuration Needed

None beyond the config change above — `customFields` in `vendure-config.ts` is read directly by `@vendure/core`'s schema generation and by the Dashboard's `useCustomFieldConfig` at runtime; there is no separate registration step.

## Frontend/Storefront Implications

None by design. The field is `public: false`, so it does not exist in the Shop API schema — there is nothing for a storefront to accidentally query or display, by construction rather than by convention.

## Tests to Add

Given this project currently has zero test infrastructure (a pre-existing gap, not introduced by this feature), the Developer stage should add a minimal, narrowly-scoped verification rather than wait for broader test tooling to be set up as a prerequisite:

- A check (e2e-style or a small script using the Admin/Shop GraphQL endpoints directly) confirming:
  1. `internalNote` is queryable/settable via the Admin API on a `ProductVariant`.
  2. `internalNote` does **not** exist on `ProductVariant.customFields` in the Shop API schema (introspection query is sufficient — this proves the structural-absence claim, not just "wasn't returned this time").

If no test runner exists to hang this on, the Developer stage should say so explicitly in `implementation.md` rather than skip verification silently.

## Risks

- **Low overall risk** — this is a config-only change using a framework-native mechanism, with no new code paths.
- **First migration in this project's history**: since `src/migrations/` doesn't exist yet, generating it is a slightly higher-stakes action than a routine "add one more migration" — the DBA stage should confirm the generated migration's `up()` only adds the new nullable column (no unexpected schema drift from the stock scaffold), and that `down()` cleanly removes it.
- **`LanguageCode` import**: a small but real risk of a TypeScript compile error if the import is missed — worth an explicit build check before considering the Developer stage done.

## Rejected Alternatives

- **A dedicated `VariantNote` entity/table via a new plugin.** Rejected: would duplicate what `customFields` already does for a single optional field, adding an entity, migration surface, and resolver code for no functional benefit over the built-in mechanism. Only justified if notes needed their own lifecycle (history, multiple notes per variant, etc.), which is explicitly out of scope per the business requirement and stories.
- **`type: 'string'` instead of `'text'`.** Rejected per the Technical PM's stated requirement to comfortably hold multi-sentence notes; `string` in Vendure's custom field types is intended for shorter, single-line values.
- **Setting `synchronize: true` to avoid writing a migration.** Rejected: this project's own README explicitly frames that as a dev-convenience tradeoff not recommended once there's production data, and the Stories require the change to be captured as a real, reproducible migration (Story 3) — sidestepping that would fail the requirement, not just cut a corner.
