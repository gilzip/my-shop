## Behavior implemented

- **Customer:**
  - set, change or remove the message on the active order during checkout;
  - the message appears in the checkout summary and in the account order details;
  - Hebrew and mixed text render right-to-left where needed (`dir="auto"`);
  - the message is never rendered as HTML.
- **Rules:**
  - 200 grapheme clusters, the same count on server and storefront;
  - line breaks and tabs kept;
  - other control characters refused;
  - HTML-like text stored as typed;
  - whitespace-only means no message.
- **Staff:**
  - edit through the dashboard or Admin `setOrderCustomFields`;
  - refused once any fulfillment is `Shipped` or `Delivered`, even if the order later moved to `Modifying`.
- **No effect on totals**, and no new API operation.

## Deviations from the architecture

- **Cart summary:** not changed. The message is entered at checkout, after the cart page; the checkout summary and the order details cover the display stories.
- **The Admin cutoff:** applies only to `setOrderCustomFields`. `setDraftOrderCustomFields` (draft orders cannot have shipped) is normalized only, as designed.

## Known limitations

- **No live database test yet.** `order.customFieldsGiftmessage` does not exist until the DBA stage generates and runs the migration. Until then, any order query on the demo server fails on the missing column. All live E2E (Shop, Admin cutoff, storefront checkout, regression) belongs to the Reviewer, after the DBA stage.
- **The storefront's gql.tada schema** now points at `localhost:3100`, so regenerating types needs the demo server running. For a permanent setup it should point at the shop's own API (`:3000`).
- **The character limit is mirrored** in the storefront (`GIFT_MESSAGE_MAX = 200`) for the live counter; the server stays authoritative.
- **Observation, outside this feature:** `order-self-cancellation` judges "shipped" from `order.state` only, so it has the same `Modifying` blind spot described in this feature's architecture. Not changed here.
